# ADR-0017: スライド指示書を「主張＋材料＋資料タイプ別の型」で書く

- **ステータス**: `提案中`
- **決定日**: 2026-09-13
- **決定者**: masaya_ueki
- **関連タスク**: #158
- **関連 ADR**: [ADR-0016](./0016-claude-design-design-system-file.md)（本 ADR はその指示書の形式を改める）／ [ADR-0018](./0018-design-system-slide-first-windows-fonts.md)（デザインシステム側の変更）

---

## コンテキスト

[ADR-0016](./0016-claude-design-design-system-file.md) で、Claude Design への入力を `docs/design/` に集約し、案件ごとの指示書（`spec.yml`）を `slide-spec-writer` スキルで作ることにした。当時の指示書は「全体構成（`deck.pages` にテンプレート ID を並べる）」「19 種のページテンプレート（ASCII レイアウト図・slots・rules）」「ページごとの `values`（表示する完成文）」で構成していた。

#152 でこの形式の指示書（`docs/design/decks/claude-handson/spec.yml`）を Claude Design に渡したところ、次のことが分かった。

1. **ページテンプレートを指定すると表現の幅が狭くなる** — レイアウト図と slots に合わせて枠を埋めるだけになる。
2. **`values` に完成文を書くとそのまま出力され、内容が簡素になる** — Claude Design が文章を組み立て直さず転記する。
3. **一方でガイドラインが無いとページが膨らむ** — 1〜2 ページのつもりの内容が 4〜5 ページに分割される。
4. **テンプレート一覧を「参考」として残すと、結局それが採用される** — 参考扱いでも拘束力を持ってしまう。

実際に配布した版（参考資料 `ハンズオン_生成AI活用推進2.pptx`）は、完成文を渡した版より説明が厚く、部品の説明ページが「なぜ必要か → 定義と特徴 → 実際のイメージ」という一貫した順序になっていた。

## 決定事項

**指示書では「何を・どのくらい」だけを決め、「どう見せるか・どう書くか」は Claude Design に任せる。** 判断基準は「それが無いと読み手が困るか」。ページテンプレートは削除し、ページごとには表示文ではなく主張（`message`）・外せない事実（`must_include`）・材料（`notes`）・書いてはいけないこと（`avoid`）・講師メモ（`speaker_notes`、全ページ必須）を書く。量は章ごとのページ上限で縛り、超えそうなら分割せず削る。情報の順序は資料タイプ別の型（`.claude/skills/slide-spec-writer/references/deck-types/<種類>.md`）で決め、型は Claude Design の良い出力から逆算して増やす。

本 ADR は `提案中` とする。claude-handson の 3〜5 ページを旧形式と新形式でそれぞれ Claude Design に出力して比べ、新形式のほうが良ければ `承認済み` にする（比較は人間が行う。旧形式の指示書は main の履歴に残っている）。

## 検討した選択肢

### 選択肢A: 主張＋材料＋資料タイプ別の型（採用）

- **メリット**: 転記されるべき完成文が無いので、Claude Design が材料から文章と図を組み立てる。レイアウトを縛らないので表現の幅が残る。章ごとの上限で量は抑えられる。型は実例（配布した資料）から作るので根拠があり、同じ種類の資料で順序と外せない要素が揃う。`deck_type` に対応する型だけを渡すので、別の種類の資料の流れに引っ張られない。
- **デメリット**: 見た目の再現性はテンプレート指定より下がり、出力ごとに配置が変わる。指示書を書く側は完成文を書くより「主張」と「材料」を切り分ける手間がかかる。型が無い種類の資料は、最初の 1 回を型なしで出力する必要がある。

### 選択肢B: ページテンプレートを「参考」として残す（不採用）

- **メリット**: 既存の 19 種を捨てずに済む。迷ったときの拠り所になる。
- **デメリット**: 参考として渡しても Claude Design はそれを採用し、選択肢 D と同じく表現の幅が狭まる。
- **不採用理由**: コンテキスト 4 のとおり、残した時点で拘束力を持つ。任せたい部分を任せられない。

### 選択肢C: ガイドラインを一切渡さない（不採用）

- **メリット**: Claude Design の表現を最も縛らない。指示書が短くなる。
- **デメリット**: 量の歯止めが無く、ページが分割されて膨らむ。講師メモや外せない事実が落ちても気付けない。
- **不採用理由**: コンテキスト 3 のとおり、1〜2 ページの内容が 4〜5 ページになる。研修の時間配分に収まらない。

### 選択肢D: 現状維持（完成文＋ページテンプレート）（不採用）

- **メリット**: 出力の見た目が指示書から予測しやすい。形式を変える作業が要らない。
- **デメリット**: 完成文がそのまま転記され、内容が簡素になる。テンプレートの枠に合わせるため、情報に合った図や構成を選べない。
- **不採用理由**: コンテキスト 1・2 のとおり、指示書の出来以上の資料にならない。

## 結果・トレードオフ

- **スキルの変更**: `slide-spec-writer` の雛形（`assets/slide_spec_template.yml`）から `page_templates` と `template` / `values` を削除し、`deck.deck_type` / `deck.max_pages` / `deck.chapters[].max_pages` と、ページごとの `message` / `must_include` / `notes` / `avoid` / `speaker_notes` に置き換えた。SKILL.md のテンプレート一覧と割り付け基準も削除した。
- **型の追加**: 最初の型として `references/deck-types/handson.md`（ハンズオン）を追加した。根拠は参考資料 `ハンズオン_生成AI活用推進2.pptx` のスライド構成。
- **渡すもの**: Claude Design には spec.yml ＋ デザインシステム ＋ `deck_type` に対応する型ファイル 1 つ ＋ materials を渡す。他の型は渡さない。
- **型の増やし方**: 新しい種類の資料は、まず型なしで出力 → 良い出力をユーザーと相談して型に起こす → `deck-types/` に追加する。机上で型を作らない（実例の無い型はテンプレートと同じ偏りを生むため）。
- **デザイン値は引き続き複製しない**: 指示書にも型にも色・フォント・文字サイズを書かず、デザインシステムを参照する（ADR-0016 の方針を維持）。デザインシステム側の分割ルール等の見直しは [ADR-0018](./0018-design-system-slide-first-windows-fonts.md) で扱う。
- **参考資料の扱い**: 参考 pptx は社内情報を含むため、公開リポジトリへのコミットを保留している。`spec.yml` の `materials:` と型の根拠節からはパスで参照し、手元のファイルを Claude Design に渡す。
- **既存案件**: `docs/design/decks/claude-handson/spec.yml` は新形式に書き換えた。`docs/design/decks/data-analysis-platform/spec.yml` は旧 `deckgen` 形式のままで、次に使うときに新形式へ書き換える。
- **見直し条件**: (1) 旧形式と新形式の比較で新形式の出力が劣ったとき、(2) 型を渡しても順序や外せない要素が守られないことが続いたとき、(3) Claude Design が指示書の公式形式を提供したとき。
