## 1. この組織は何か

**収益仮説を立て、作り、公開し、売上を見て次の仮説を決める** ——この一周を Claude のエージェント群で回すための組織である。

重要な前提が 2 つある。

- **組織そのものは収益を生まない。** 収益を生むのは売れる商品であり、組織は**試行回数を増やす装置**にすぎない。
  組織の作り込みが目的化していないかは [5. 撤退・継続の基準](#5-撤退継続の基準) で定期的に問う。
- **役職を並べただけの「AI 会社ごっこ」を作らない。** 各役割は前の役割の成果物を入力に取り、次の役割が使える形で出力する。
  入出力が繋がらない役割は置かない。

組織は life-os 内に置き、売り物だけを別リポジトリへ切り出す 2 層構成をとる。理由は [ADR-0014](../../docs/adr/0014-revenue-org-inside-life-os.md) を参照。

## 2. 役割と担当（誰が何を受け取り、何を出すか）

新規に作るのは、既存の開発 loop に**欠けていた両端**（仮説の入口と公開の出口）だけ。
中間の PO・実装・レビューは life-os の既存資産をそのまま使う。

| # | 役割 | 実体 | 入力 | 出力 |
|---|------|------|------|------|
| 1 | リサーチャー | [`biz-market-scout`](../../.claude/agents/biz-market-scout.md)（新規） | 関心領域・制約（工数・スキル） | 収益仮説を ProductBacklog Issue として起票 |
| 2 | プロダクトオーナー | [`scrum-notion-pbi`](../../.claude/skills/scrum-notion-pbi/SKILL.md) / [`issue-memory`](../../.claude/skills/issue-memory/SKILL.md)（既存） | 収益仮説 Issue | PBI と Task Issue に分解 |
| 3 | エンジニア | [`issue-loop`](../../.claude/skills/issue-loop/SKILL.md)（既存） | Task Issue | 実装 → PR |
| 4 | レビュア | [`pr-reviewer`](../../.claude/agents/pr-reviewer.md) / [`review-and-merge-pr`](../../.claude/skills/review-and-merge-pr/SKILL.md)（既存） | PR | 検証済みのマージ、または修正 PR |
| 5 | マーケター | [`biz-launch`](../../.claude/agents/biz-launch.md)（新規） | マージ済みの完成物 | 価格案・LP 文面・告知文の**草案**（公開はしない） |
| 6 | 経理 | [`content-sales`](../../domains/content-sales/README.md) 領域（既存・実装は #125） | 売上・コストの記録 | 期間 KPI（売上・コスト・粗利・件数） |
| 7 | 経営 | `biz-review` スキル（#126 で追加予定） | KPI + Open な仮説の状況 | 継続 / 撤退 / 次の仮説の**素案** |
| — | 人間（あなた） | — | 5・7 の草案・素案 | **承認・却下・実行**（[4. ハードストップ](#4-ハードストップエージェントに実行させないこと)） |

> エージェントの詳細な手順は各エージェント定義ファイルが正本。ここでは繋がりだけを定義する。

## 3. 収益 loop（1 周の流れ）

```
        ┌──────────────────────────────────────────────────────────┐
        │                                                          │
        ▼                                                          │
 ① biz-market-scout ──▶ ② PBI/Task 分解 ──▶ ③ issue-loop ──▶ ④ pr-reviewer
    収益仮説を起票          （既存スキル）        実装 → PR         レビュー → マージ
                                                                   │
                                                                   ▼
                                                            ⑤ biz-launch
                                                          価格・LP・告知の草案
                                                                   │
                                                          ▼ 【人間承認】公開
                                                                   │
        ⑦ biz-review ◀────────── ⑥ content-sales ◀────────────────┘
      継続/撤退/次の仮説の素案      売上・コストを記録 → KPI
        │
        ▼ 【人間承認】
        └─▶ ① へ戻る（次の仮説）
```

**この loop の肝は ⑥ → ⑦ → ① の帰り道**である。売上という事実が次の意思決定の入力に戻ることで、
[Loop Engineering](../development-policy/loop-engineering.md) が言う「loop が自分で次を決める」状態に近づく。
行き（①→⑤）だけを作っても、それは並列セッションの束であって loop ではない。

### 最初の一周は 3 点だけで回す

最初から 7 役割すべてを作らない。`biz-market-scout` → `issue-loop` → `biz-launch` の 3 点で一周し、
**売上がゼロでも「仮説 → 検証 → 撤退判断」が回るか**を先に確かめる。⑥⑦ は #125 / #126 で追加する。

## 4. ハードストップ（エージェントに実行させないこと）

以下はエージェントが**草案の作成まで**を行い、**実行は必ず人間が行う**。エージェントに実行権限を与えない。

| 対象 | エージェントがやること | 人間がやること |
|------|----------------------|---------------|
| 課金・決済の設定 | 価格案とその根拠を提示 | 決済サービスへの登録・価格の確定 |
| 外部公開（リリース・ストア掲載） | LP 文面・説明文の草案 | 公開ボタンを押す |
| 対外発信（SNS・ブログ・告知） | 告知文の草案 | 実名アカウントからの投稿 |
| 送金・出金・契約 | — | すべて |
| 顧客対応（問い合わせ返信） | 返信案の下書き | 送信 |

**理由**: これらは取り消しが効かず、失敗が金銭・信用・実名に直接跳ね返る。
loop の速度を上げる価値より、暴走時の損失のほうが大きい領域には歯止めを置く。

あわせて、生成物には次の制約を課す。

- 実在する企業・人物・サービスを騙る文面を作らない。
- 実績・レビュー・利用者数を**事実でない形で**書かない（「〇〇人が利用」等は実データがある場合のみ）。
- 競合製品を名指しで貶める比較を書かない。

## 5. 撤退・継続の基準

「なんとなく続ける」を防ぐため、判断を数値で定める。判定は `biz-review`（#126）が行い、**実行は人間が承認する**。

| 判定 | 条件 | アクション |
|------|------|-----------|
| **撤退** | 公開から 8 週間、売上が 0 件 | Issue をクローズし、学びを [`continuous-learning`](../../.claude/skills/continuous-learning/SKILL.md) に蓄積 |
| **縮小** | 粗利がマイナス（運用コスト > 売上）が 4 週間継続 | 運用コストの削減 or 値上げの素案を出す |
| **継続** | 上記いずれにも該当しない | 次の改善仮説を 1 件起票する |
| **組織の見直し** | 直近 12 週間で公開に至った仮説が 0 件 | **組織の作り込みが目的化している**と判断し、組織側の作業を止めて商品側に寄せる |

最後の行は組織自身への歯止めである。エージェントを増やすこと自体は収益に寄与しない。

## 6. Issue・ラベル運用

Issue の分類・ラベル・ブランチ・コミットの規約は
[Issue 運用ルール](../development-policy/issue-operation-rules.md) に従う（ここでは重複させない）。
収益組織に固有の運用は次の 2 点だけ。

- **収益仮説は ProductBacklog Issue として起票する。** 仮説は必ず「調査 → 実装 → 公開」の複数フェーズを伴うため。
- **`system:` ラベルは新設しない。** 売上・KPI・販売物に関することは `system: content-sales`、
  エージェントや運用ルールなど組織横断のインフラは `system: common` を使う。理由は [ADR-0014](../../docs/adr/0014-revenue-org-inside-life-os.md) を参照。

## 7. やらないこと

- **売り物のコードを life-os に置き続けない。** 公開判断に至った時点で別リポジトリへ切り出す（[ADR-0014](../../docs/adr/0014-revenue-org-inside-life-os.md)）。
- **役割を先回りして増やさない。** 表の 7 役割で回らない事実が観測されてから足す。
- **売れる前に決済・分析・顧客管理の基盤を作らない。** 必要になった時点で `content-sales` の `adapters/` に足す。
- **一周回す前に組織のドキュメントを増やさない。** 正本はこのファイル 1 つに保つ。
